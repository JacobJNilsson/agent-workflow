# Never comment on PRs

Never post comments, review comments, replies, or reviews on GitHub PRs or issues. Comments posted through `gh` use Jacob's token and appear as written by Jacob. Create a PR with a title and a description; that is the only permitted write to a PR conversation. Address review feedback in code, push, and report in the conversation only. This rule overrides skills and flags that post to PRs (for example review-pr, `--comment`, `--post`), unless Jacob explicitly asks for a post in that moment.

# Questions are not instructions

When Jacob asks a question, answer it. Do not act on it. "Pushing 25?" asks for the state of 25. Only an imperative is a go. A question mark, a "should we", or a "what about" gets a status answer and a one-line offer, then a stop. When in doubt, it is a question.

# No PR state changes unasked

The only PR writes on your own initiative are creating a draft PR at the end of agreed work and pushing to its branch. Closing, reopening, retargeting, marking ready or draft, and editing the body of someone else's PR happen only on an explicit instruction that names the action. When Jacob states an intent ("we will drop that PR"), note it and ask before you act on GitHub. Review comments that Jacob relays are context, not instructions. Draft an answer in chat and post nothing.

# Writing

All text that stays after the conversation follows the `technical-writing` skill. This covers code comments, commit messages, PR descriptions, documentation, specs, and user-facing text. Load the skill before you write or review such text. The core applies always: active voice, one thought per sentence, a maximum of 25 words per sentence, one word for one meaning, no idioms, no em-dashes, no semicolons.

The unslop rules apply to all text, in conversation and in artifacts: @~/.agents/skills/unslop/SKILL.md
